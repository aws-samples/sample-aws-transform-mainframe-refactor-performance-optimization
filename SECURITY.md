# Security Policy

> **Important:** This is sample code for demonstration and testing only.
> It is **not intended for production use**. The Tomcat server, database
> configuration, and batch job endpoints have no authentication or TLS, and the
> database role relies on passwordless loopback trust. Before using any part of this code in production,
> complete your own security review and apply the hardening steps below.

## Reporting a Vulnerability

If you discover a potential security issue in this project, we ask that you
notify AWS/Amazon Security via our
[vulnerability reporting page](http://aws.amazon.com/security/vulnerability-reporting/)
or directly via email to [aws-security@amazon.com](mailto:aws-security@amazon.com).

Please do **not** create a public GitHub issue for security vulnerabilities.

We prefer all communications to be in English.

## Scope and Intent

This repository is **sample / reference code**. It contains a z/OS COBOL/DB2
securities trading application that was refactored to Java with AWS Transform for
mainframe, and it exists so that a performance optimization workflow can be
demonstrated on a realistic batch job (`ACCPCAD` / program `TRDPB000`).

It is a local developer setup: Apache Tomcat 10.1 on Java 21 with a local
PostgreSQL database, driven by `curl` from the same machine. It deploys no AWS
infrastructure. It is **not** production-ready and carries no warranty. Review it
against your own security, compliance, and cost controls before any real use.

The trading data is entirely synthetic, generated by
`database/generate_cad_data.sql`. There is no real customer, account, or
financial data anywhere in this repository.

## Known Gaps in This Sample

These are deliberate, because they keep the sample small and runnable. Each one
must be closed before any part of this code is used in production.

### 1. No authentication or authorization

Every endpoint is open. `GET /gapwalk_application/script/<JOB>` starts a batch
job that writes to the database. Any caller who can reach the port can start
`ACCPCAD`, `SETLCAD`, `EXECRPT`, or any other job, change trading data, and
repeatedly run the 200,000-order job against the 4 GB heap. The same applies to
the terminal transactions served to the web front end.

The one filter in the application, `ValidationFilter`, does not help. It wraps
each request in `ValidatingHttpRequest`, which extends
`HttpServletRequestWrapper` and overrides nothing, so no validation takes place.
It is also mapped only within the `app_service` web application, while the batch
job endpoints are served by the separate `gapwalk_application` context — so the
filter never sees them even if it did validate.

**For production:** enable the AWS Transform for mainframe runtime's Spring
Security / OAuth2 configuration and protect `/gapwalk_application/*` with Amazon
Cognito or your own identity provider. Restrict job-trigger endpoints to an
operator role, and replace `ValidationFilter` with an allowlist of permitted job
names and parameters.

### 2. HTTP only, no TLS

The only connector in `server/conf/server.xml` is plain HTTP on port 8080. The
8443 TLS connector is commented out, because a sample cannot ship a keystore or
a certificate safely. Session identifiers (`X-Auth-Token`) and screen data such
as customer IDs and account balances therefore travel unencrypted.

**For production:** terminate TLS 1.2 or later on an internal Application Load Balancer
 using an AWS Certificate Manager certificate. If you instead enable the
8443 connector directly, source the keystore password from AWS Secrets Manager —
never leave it as `changeit`.

### 3. Database privileges are split, but authentication is not enforced

The three datasources in `server/conf/server.xml` (`jdbc/bluesam`, `jdbc/blu4iv`,
`jdbc/primary`) log in as `tradingapp_app`, a role with `SELECT`, `INSERT`,
`UPDATE` and `DELETE` on the `tradingapp` tables and nothing else. It has no DDL
privileges and no `TRUNCATE`. The role is created at the end of
`database/tradingapp_pg.sql`.

This limits the damage any SQL reaching the database can do — for example through
an injection bug introduced in adapted code. It does not authenticate the
application: the role has no password, because local loopback connections are
expected to be trusted (see gap 4).

**Do not change the datasources back to a superuser** to resolve a permissions
error. With superuser access, SQL reaching the database could read other
databases, create roles, or run operating system commands through
`COPY ... PROGRAM`. If a statement fails on privileges, run it under the
administrative login instead.

**For production:** keep this split, give the role a managed credential, and
apply the same separation to any new schema you add.

### 4. No secrets store for database credentials

The datasource `password` attributes are empty. That works because local
PostgreSQL connections use peer or trust authentication on a developer machine.
There is no integration with a secrets manager, because this sample deploys no
AWS infrastructure.

**For production:** store database credentials in AWS Secrets Manager with
rotation enabled, or use Amazon RDS IAM database authentication. Inject them
through the runtime datasource configuration or `aws-secretsmanager-jdbc`. Never
place a password in `server.xml` or commit one to source control.

### 5. The server is deliberately restricted to loopback

Because of gap 1, the port 8080 connector in `server/conf/server.xml` sets
`address="127.0.0.1"`. Tomcat therefore accepts connections only from the local
machine. This is a containment measure, not a fix: the endpoints remain
unauthenticated, and removing the `address` attribute exposes every batch job to
anyone who can reach the port — on shared Wi-Fi, a corporate subnet, or an EC2
instance with a permissive security group.

**Do not remove it** to reach the application from another machine. Use an SSH
tunnel, or add authentication first.

Note that Tomcat reads `server.xml` from `CATALINA_BASE`, which is not always
this repository. If you launch the server from an IDE, confirm which
`conf/server.xml` is actually in use and that the `address` attribute survived
into it.

## Security Debt Register

The three items below are accepted debt for this sample rather than defects. Each
is recorded with its severity, why it is accepted here, what happens if it is
carried into a real deployment, and the remediation to apply.

Security review date: 2026-10-28. Target date for closing all three items:
**2027-01-26**.

### Debt 1 — No application-layer authentication (MEDIUM)

`ValidationFilter` performs no validation, and nothing authenticates callers. See
gap 1 above for the mechanism.

**Why accepted here:** adding authentication requires Spring Security or an
external identity provider, which is an architectural change rather than a
configuration change. The risk is contained by the loopback bind (gap 5).

**If unaddressed:** anyone who deploys this on Amazon EC2 or in a container and
removes the loopback bind leaves every batch job and every terminal transaction
open to anyone who can reach the port.

**Remediation:** enable the AWS Transform for mainframe runtime's Spring Security
/ OAuth2 configuration and protect `/gapwalk_application/*` with Amazon Cognito
or your own identity provider. Restrict job-trigger endpoints to an operator
role, and replace `ValidationFilter` with an allowlist of permitted job names and
parameters.

### Debt 2 — HTTP only, no TLS (MEDIUM)

Plain HTTP on port 8080. See gap 2 above.

**Why accepted here:** traffic is loopback only, and a certificate and keystore
cannot be shipped safely inside a sample.

**If unaddressed:** in a networked deployment the `X-Auth-Token` session
identifier — used by the Angular front end in `transaction.service.ts` and
`user-info.service.ts` — and the screen data it carries, including customer IDs
and account balances, can be intercepted and replayed.

**Remediation:** terminate TLS 1.2 or later on an internal Application Load Balancer
 with an AWS Certificate Manager certificate. Alternatively, enable the
8443 connector with a keystore whose password comes from AWS Secrets Manager —
never `changeit`.

### Debt 3 — No secrets store for database credentials (LOW)

Credentials are not held in a secrets manager. See gap 4 above.

**Why accepted here:** appropriate for a local PostgreSQL instance. AWS Secrets
Manager requires AWS infrastructure that this sample does not deploy.

**If unaddressed:** users moving to Amazon RDS are likely to put the master
password directly into `server.xml` and commit it. That file is tracked in git,
so the credential would be published.

**Remediation:** store credentials in AWS Secrets Manager with rotation enabled,
or use Amazon RDS IAM database authentication. Inject them through the runtime
datasource configuration or `aws-secretsmanager-jdbc`.

## Database Privileges and Credentials

Two logins are involved, and they are not interchangeable:

| Login | Used for | Notes |
|---|---|---|
| `postgres` (superuser) | Schema creation and test data: `database/tradingapp_pg.sql`, `database/generate_cad_data.sql`, `database/reset_cad_run.sql` | These scripts issue `DROP TABLE`, `CREATE TABLE`, and `TRUNCATE`. |
| `tradingapp_app` | The application datasources in `server.xml`, runtime DML only | `SELECT`, `INSERT`, `UPDATE`, `DELETE` on the `tradingapp` tables. No DDL, no `TRUNCATE`. |

If a `TRUNCATE` or `CREATE` fails at runtime, the fix is to run that statement
under the administrative login, not to grant more privileges to the application
role.

Do not set a password in `server.xml`. If your local PostgreSQL requires one,
configure peer or trust authentication for local connections in `pg_hba.conf`
instead, and restrict it to `127.0.0.1`.

The PostgreSQL JDBC driver (pgjdbc) on the Tomcat/runtime classpath must be
version 42.7.14 or later. Earlier versions are affected by CVE-2026-42198
(unbounded SCRAM PBKDF2 iterations), CVE-2026-54291 (channel-binding downgrade),
GHSA-rhp9-mr79-r74h (`requireAuth` bypass) and GHSA-f64h-wr5q-3qf3 (stale bytes
in `ByteStreamWriter` values). Use the latest 42.7.x release. The project
`pom.xml` declares 42.7.14.

## Dependencies

The front-end lockfile (`app-pom/app-web/angular/package-lock.json`) was
refreshed within the declared version ranges. `npm audit --omit=dev` reports
0 vulnerabilities, so nothing shipped to the browser has a known advisory.

`npm audit` still reports moderate advisories in packages that are
**dev-toolchain only, not shipped**: the Angular CLI and build tooling
(`@angular/cli`, `@angular-devkit/build-angular`), the ESLint plugin, the Karma
test runner and reporters, and `stylus`. All of these advisories trace back to
older `glob` and `minimatch` versions pulled in by those tools. Fixing them
requires `npm audit fix --force`, which installs SemVer-major versions outside
the supported Angular 20 toolchain, so they are left in place. They run only on a
developer machine during `ng build`, `ng serve` and tests. Do not expose
`ng serve` beyond localhost.
